## 1. 范围与所有者

本期目标是：客服总监、客服经理可直接配置权限；配置不经过审批。客服总监、客服经理、客服主管、客服组长均可在负责范围上传Excel和发布资料，发布前必须弹窗二次确认。主管/组长不因上传发布取得配置他人权限；普通客服查询、选择并复制。资料仍经过文件解析、规范化、来源确认与质量检查；取消人工审批不取消这些资料正确性和权限门。

权限配置复用既有 grants 接口和事实/范围/CAS/审计事务，不增加审批模板或新权限管理服务。上述两类岗位依据已确认身份及精确部门/岗位映射获得角色上限，角色标签本身不代替店铺/来源范围及分配资格。分配权限与业务权限的区分、不得自我提权/超范围/再转授等规则保留；本期配置资格仅按总监/经理名单收敛，旧个人委派不自动让其他岗位继续配置；不因为可配置权限就自动拥有全部店铺。首次范围与用途角色装配仍需明确登记，本候选不自行给真实人员授权。

`authorization_deadline` 与产品 overlay 0030 使用同一 HAVING：director、manager、supervisor、lead 在有效 business grant 上，该业务动作的期限非空；agent 与历史角色 enabler 仅在 `p_action='query'` 时非空。历史 grant 行不删除，也不改写成 direct-v1。enabler 不在本期上传发布名单。enabler/agent 留下的旧非 query business grant 不再放行新的 publish、import 或其他业务操作。本函数不授予应用角色，也不证明分配凭证。岗位仍然不代替店铺、来源和内容范围。

现有 storage 没有单独的分配函数，本增量不新造该函数，也不新增第二套审批表。分配兼容规则写在这里：只有 director、manager 可配置他人权限；supervisor 没有 allocation；其他角色不能再用 delegation 分配；新 delegation 的接收人仅 director、manager；禁止再转授，沿用既有 `may_redelegate=false`。这些分配限制不由 `authorization_deadline` 证明。质量检查、来源确认、版本冲突、原子提交和未知结果恢复都保留。取消人工审批不得变成伪造审批通过，也不得把质量检查做成另一套审批。

直发 wire 保持不变：IntakePublish 与 IntakeRollback 必须 `confirmed: true`，拒绝 `approvalEvidenceVersion`；`publicationPolicy` 为 `approval-v1 | direct-v1`。本轮不扩展 SOP 或自动同步，也不把上述 SQL 上限当成四岗产品端到端验收。资料格式、来源、质量检查继续保留，不新增人工审批人。

并行推进：身份/授权所有者对齐岗位、范围和失效；发布所有者接入免审批发布、回退与读端；来源/运行所有者准备店铺名称、初始认领、受限账号及装配；验收所有者准备四岗/普通客服与错误/撤权/断网案例。共享机器合同、迁移编号和发布目录由同一集成人维护，最终在接口稳定后汇合验证；实际人员/环境信息缺失只阻塞对应落地。本次不新增业务模块。

治理仓拥有机器合同和本规范。产品 API 拥有候选发布政策、当前权限、资料门、原子发布和持久回执；数据库拥有不可变历史及关联约束；Main 拥有二次确认、精确待提交输入与取消代际；renderer 只提供发布意图，不能回传权限或审批结论。现有唯一发布指针、公告、目录、审计及恢复路径继续复用。

比较两个边界：A 是只移除界面审批按钮并在内部补一个 approved，仍依赖虚构证据且无法一致处理历史；B 是显式版本化发布政策，新候选直发、旧记录保留原政策，服务端和消费者同时调整。选择 B。确认也放在已有 Main 原生能力中，复用原 IPC 命令，避免新增可伪造“弹窗已确认”的 renderer 通道。

## 2. 直发 wire 与状态

`IntakePublish` 与 `IntakeRollback` 不再接受 `approvalEvidenceVersion`，必须有 `confirmed: true`；缺失、false、其他类型及附带旧审批字段拒绝。其余精确候选 key、来源确认版本、baseReleaseId、回退计划/impactDigest、operationId 和发布说明保持原约束。布尔值表达本次意图，不是服务端权限，也不能证明任意第三方 HTTP 客户端真的展示了弹窗。

`IntakeCandidate.publicationPolicy` 为服务端字段：`approval-v1 | direct-v1`。新 profile 下 receive/revise 固定创建 direct-v1；客户端不得选择该政策。direct-v1 的 approvalEvidenceVersion 恒为0（仅为兼容读取保留），不创建审核包、review binding、approval fact、reviewer ticket。ready 取决于当前来源、材料、质量等现存门，不再因 AWAITING_APPROVAL/HUMAN_REVIEW_REQUIRED 阻塞，也不伪报审核通过。常规稿与关键稿都不需要人工审批；风险标记仍用于资料检查/展示，不能据此恢复审批要求。

回退影响预检的 approvalEvidenceVersion 保留兼容字段：新直发计划返回0，既有计划历史读取可以保留原值，但该字段不进入新直发请求或授予资格。

新 profile 下四个 review POST（候选/回退的发起和刷新）返回409 CONFLICT / MODE_CONFLICT；旧 GET 仅保留历史查看，无续期副作用。管理界面移除新候选的审批操作和作为发布条件的审批提示。历史读取不得虚构 direct-v1 的审核人。

首次直发只接受 direct-v1 候选；旧未发布候选必须由用户显式 revise 或重新导入为新版本，不能原地换政策。旧未知提交仍按旧 operationId 和原始载荷查回执，绝不能重编码为 confirmed=true 的新请求重复执行；旧协议恢复适配必须保持原摘要和原政策，无法安全恢复时只读历史回执并给出可见提示。新请求的确认标志纳入 payload digest；同 operationId 不同输入仍冲突。

## 3. 二次确认与提交边界

点击发布后 Main 冻结候选 key、来源、标题/说明、base 和操作输入，打开原生警告弹窗，默认/关闭均为取消。确认后先检查取消代际和当前权限，再发送冻结的请求。取消不登记待提交操作、不请求发布接口，保留编辑内容；对话框期间重复提交、换候选不能绕过单操作状态。退出登录、切换会话、窗口销毁或权限到期后的迟到确认不得发请求。未装配原生确认依赖失败关闭。

服务端不依赖按钮状态或 confirmed 字段授予权限。提交事务仍复核会话、启用且新鲜的组织事实、动作和所有影响来源的 scope、来源确认版本/代际、不可变材料、质量结果、内容有效期、base CAS、容量/目录完整性。提交票据移除直发的审核人/审批字段，保留 actor 事实、撤销代际、来源集合和至多60秒期限；提交前再验期限。一次原子提交写发布、公告、current、审计、回执；未知响应使用已确认原输入查回执/重试，不改 base 后盲重放、不重复弹窗诱发第二个操作。

纠正回退已有独立权限和全范围影响预检；作为新的发布同样取消人工审批、要求确认，继续生成新 release，不移动指针来假装回到过去。确认需显示目标及影响；预检后的并发发布、目标失效或范围权限变化必须拒绝。此候选不新增回退业务。

## 4. 存储与历史兼容

schema.v1.22 在完整1.21后追加增量；没有应用角色授权或生产装配。候选、attempt、ticket、publication、lineage 新增不可变 publication_policy，默认 approval-v1 使已有行保留历史。新 direct-v1 行由服务端显式写入；跨政策关联由复合外键拒绝。

直发候选审批版本为0，直发 attempt 审批版本为NULL，直发 ticket 审核人/审批版本及代际为NULL，直发 lineage review_request_id 为NULL。legacy 分支保持对应字段要求；不得用NULL弱化历史检查。publication 的 direct-v1 必须记录有限 confirmed_at（服务端确认请求受理时间，不能当客户端点击的可信时钟）；legacy 为NULL。既有不可变触发器覆盖新列，不能改写旧政策/确认时间。

数据库 readiness CHECK 只表达最低存储形状；它不证明权限、质量或原子提交完整性。产品交易层、catalog reader、entitlement/snapshot 与 rollback_lineage overlay 必须同时按政策分支接入：direct-v1 不查询不存在的审批；approval-v1 继续原审核谱系与内容期限/撤销检查。不得将旧审批被撤销、过期的内容作为“新直发”重新激活；需显式新候选走完整资料门。混合目录允许两种来源历史，但每项来源追溯和期限各自保留，不能因新条目直发而跳过旧条目检查。

增量末尾用 `CREATE OR REPLACE FUNCTION content_intake.authorization_deadline` 替换前序业务上限。替换只影响新的非 query 业务操作如何被拒绝；它不删除历史 grant，不改写旧 approval-v1 行，也不给 direct-v1 补审核人。direct-v1 仍然不制造审核人。没有应用角色授权，也没有生产装配。
