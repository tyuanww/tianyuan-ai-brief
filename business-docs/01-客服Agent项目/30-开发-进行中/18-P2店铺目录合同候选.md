## 边界

方案 A 把 `displayName` 放进每个 Source。同店的售前与商品来源会各自改名，分页时能拼出两个名字。方案 B 使用独立的 tenant/app/shop 目录，一个店铺只有一条当前名称和 `displayVersion`。本候选采用方案 B。`shopId` 继续拥有查询和复制身份；名称只替换菜单文案。

比较过的失败面：A 的写入面更小，但读结果会随来源漂移。B 多一张目录和一次修订，读路径却能用同一谓词给出一份完整集合。任务要求同店不同来源的名称和版本一致，因此取 B。

## 读合同

`GET /v1/intake/shop-directory`，`operationId` 为 `listIntakeShopDirectory`。认证只来自 `ProductSession`。调用方不能提交 principal、tenant、app、会话哈希或店铺名单。`limit` 为 1–100，缺省 50。响应 `Cache-Control: no-store`，正文是 `{items, nextCursor, validUntil}`。每条 item 只有 `shopId`、`displayName`、`displayVersion`。

`displayName` 为 1–256 个 Unicode 字符，不含控制字符和行分隔符，首尾不能是 ECMAScript 空白（含制表、NBSP、全角空格、BOM）。SQL 和 JSONSchema 使用同一字符规则。单页最多 100 条，UTF-8 响应预算为 128 KiB，包含最长合法 Unicode 名称和 ID 的边界验证。重名保留各自 `shopId`。`shopId = null` 的品牌范围不进入目录，也不能展开成全公司店铺。名称不授予 query 或其他业务动作。

服务端先用既有 `content_intake.authorization_deadline(principal, 'query', scope, source, at)` 得到可见店铺。只计入 `sources.mode = 'v2-preview'` 且 `scopes.shop_id IS NOT NULL` 的来源。任一来源的 query 期限非空，该店出现一次。legacy、v2-active、无 query 期限的店不出现。空集合返回空 `items`，这不是缺名称。可见集合里任一店没有当前名称时，整次 `409 SHOP_DISPLAY_MISSING`，不返回其余店。

只读失败追加在既有 `IntakeFailure.details.reason` 末尾，且只用于这个 GET：

| reason | HTTP | 含义 |
| --- | --- | --- |
| `SHOP_DIRECTORY_CURSOR` | 400 | cursor 或 limit 不符合合同，签名、limit 或页边界被篡改，或换了会话 |
| `SHOP_DIRECTORY_SESSION` | 401 | 主体不存在，或 ProductSession 未认证 |
| `SHOP_DISPLAY_MISSING` | 409 | 当前可见店缺少名称；调用方继续显示编号，不得用编号冒充名称 |
| `SHOP_DIRECTORY_CHANGED` | 409 | 事实版本、撤销代际、目录修订或可见集合摘要已变 |
| `SHOP_DIRECTORY_EXPIRED` | 409 | 主体事实不可用，或游标截止已到 |

以上失败都不返回 `items`。CHANGED 与 EXPIRED 后必须丢弃已读页，从第一页重读。不得把旧页和新页拼成一份目录。

## 游标

`nextCursor` 为 `sd2.<factsVersion>.<revocationGeneration>.<directoryRevision>.<sha256>.<deadlineEpochUs>.<ordinal>.<limit>.<lastShopId>.<signature>`，总长不超过 512；不外发会话哈希。HMAC 签名绑定主体、tenant、app、会话及完整载荷。签名使用独立的服务端私有 `p_cursor_signing_key`（32 字节），不使用会话哈希或 bearer 派生值作 key；知道自己 token 的客户端仍不能重签。签名、页大小或会话不匹配均为 `SHOP_DIRECTORY_CURSOR`；修改序号和店铺两字段也不能跳页。

`sha256` 是按 `C` 排序的 `shopId:displayVersion` 用逗号连接后的摘要。`ordinal` 是完整有序集合中的 1 起序号。截止为事实有效期和所有可见店 query 期限的最小值，截断到毫秒；空集合用事实截止。续页不得延长最初截止，即使期间授权续期；当前截止缩短则 `SHOP_DIRECTORY_CHANGED`。事实代际、目录修订或集合摘要变化要求整份重读。

存储接口为 `read_shop_directory(principal, session_hash, at, cursor, limit, cursor_signing_key)`。服务端填入身份、会话、校验时间及签名材料，不接受 HTTP 调用方传这些字段。存储函数以 `greatest(p_at, clock_timestamp())` 在获得目录锁后验证当前 enabled 事实及身份，页面构建和 HMAC 结束、RETURN 前再检查真实时钟。目录锁等待不能用请求旧时间绕过到期。可见集合物化为一个 jsonb 值，避免池内临时表计划失效；名称缺失仍整单拒绝。

本函数只把 `session_hash` 绑定到游标，不直接查询或验证 `backend_identity.sessions`，不能单独充当 ProductSession 验证器。未来受信调用者必须先验证当前会话与身份，沿既有会话／全局内容／撤权锁序执行，在同一事务末尾重新检查会话、来源／query 资格与最早截止；不允许返回过期结果或提交过期维护写入。函数内行锁和目录锁不是外层会话锁的替代品。当前无产品消费者；这些调用者接线、锁序并发和事务末尾截止的集成验证仍是冻结／接入前条件。

## 写入所有者

没有写 HTTP。名称只能由 `content_intake.upsert_shop_display(actor, tenant, app, shop, display_name, expected_revision)` 写入。

写入者必须是 `content_intake.shop_directory_stewards(tenant_id, app_id)` 里登记的主体，并且该主体属于同一 tenant/app，身份绑定未停用，当前事实 enabled 且新鲜。取得目录锁后与写入结束前都复核截止；停用或到期不能继续更名。没有这行就失败关闭。登记行拒绝 UPDATE 和 DELETE。本候选不提供自助登记，不从岗位、飞书通讯录或品牌授权生成维护人。真实维护人尚未提供，测试只显式插入合成主体 `steward` / `steward-b`。

`expected_revision` 为空只允许在该 tenant/app 还没有目录修订时使用。之后必须等于当前修订，否则 `SHOP_DIRECTORY_CONFLICT`，并且不增加 `displayVersion`、不改当前指针。成功时追加历史行，`displayVersion` 从 1 递增，目录修订按 tenant/app 加 1。历史行拒绝 UPDATE 和 DELETE。当前指针和修订只有在事务局部 GUC `content_intake.directory_write=writing` 下才能写，这个 GUC 只是函数内部一致性标记，不是权限门；PostgreSQL 调用方能自行 SET 自定义 GUC。真正边界是应用角色没有新表写权限和函数执行权限，实库用 SET ROLE + SET GUC 验证仍被拒绝。函数成功后清空标记；未来用途 ACL 需独立批准，不可据此给表直写权限。同一 tenant/app 的写用事务级 advisory lock 串行。

写入失败留在 SQL，不进入 OpenAPI：`SHOP_DISPLAY_INVALID`、`SHOP_DIRECTORY_STEWARD_REQUIRED`、`SHOP_DIRECTORY_CONFLICT`、`SHOP_DISPLAY_IMMUTABLE`。upsert 不插入 grant。

## 和现有库的差异

新表只有 `shop_directory_stewards`、`shop_directory_revisions`、`shop_displays`、`shop_display_current`。`sources` 不增加名称列。授权谓词仍是 schema.v1.22 里的 `authorization_deadline`，包括四岗业务上限和 agent/enabler 新操作只 query 的 HAVING。本候选不修改该函数，不修改产品 `authority.ts`，也不占用产品 overlay `0030` 或后续 migration 编号。新增函数和四张新表都 `REVOKE ALL FROM PUBLIC`。

## 产品最小接线

产品仓在批准、export、intake 和 codegen 之前不消费本候选。接线所有者是主 Agent，落点是 `loadIntakeAccess`：用同一个 ProductSession 把目录页读完，页集合的 `shopId` 必须与现有 `shops` 完全一致，只把 `IntakeQueryFilters` 里 option 的可见文案换成 `displayName`，option 的值仍是 `shopId`。任一页失败则整份菜单失败，继续显示编号。不新增 renderer preload channel。query 和 copy 仍传 `shopId`。品牌授权继续不能变成全公司店铺。建议补丁只在冻结 intake 之后修改 `content-intake-access.ts`、`IntakeQueryFilters.tsx`、合同锁和 codegen；本候选不修改这些文件。

## 尚缺的业务决定

- 真实目录维护人、谁有权登记／撤销／轮换，以及轮换的审计与 CAS 规则。本候选已拒绝停用和过期维护人，但登记行仍不可变，缺少可执行轮换规则，因此尚不满足冻结条件。
- 每个真实店铺的正式名称由谁确认。这里的名称全部是合成 fixture，不能当成飞书已经提供了业务店铺名。
- 正式游标签名 key 的受限注入与轮换安排。当前仅合成固定 key，未创建或读取任何真实 secret，产品没有装配。未来 key 只允许受信目录服务及其受限数据库调用持有，禁止进入 renderer、HTTP 请求参数、日志和错误；存储函数没有应用角色 EXECUTE，后续授予用途权限须独立核验。持钥方配置、key 有效期与轮换时点尚未批准；换 key 后旧游标拒绝并重新读第一页。
- A/B 回收后 1.21.0 / schema.v1.23 是否仍是批准版本号。
