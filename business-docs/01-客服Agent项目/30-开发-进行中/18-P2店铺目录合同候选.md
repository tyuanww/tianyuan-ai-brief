## 边界

方案 A 把 `displayName` 放进每个 Source。同店的售前与商品来源会各自改名，分页时能拼出两个名字。方案 B 使用独立的 tenant/app/shop 目录，一个店铺只有一条当前名称和 `displayVersion`。本候选采用方案 B。`shopId` 继续拥有查询和复制身份；名称只替换菜单文案。

比较过的失败面：A 的写入面更小，但读结果会随来源漂移。B 多一张目录和一次修订，读路径却能用同一谓词给出一份完整集合。任务要求同店不同来源的名称和版本一致，因此取 B。

## 读合同

`GET /v1/intake/shop-directory`，`operationId` 为 `listIntakeShopDirectory`。认证只来自 `ProductSession`。调用方不能提交 principal、tenant、app、会话哈希或店铺名单。`limit` 为 1–100，缺省 50。响应 `Cache-Control: no-store`，正文是 `{items, nextCursor, validUntil}`。每条 item 只有 `shopId`、`displayName`、`displayVersion`。

`displayName` 为 1–256 个 Unicode 字符，不含控制字符和行分隔符，首尾不能是 ECMAScript 空白（含制表、NBSP、全角空格、BOM）。SQL 和 JSONSchema 使用同一字符规则。单页最多 100 条，UTF-8 响应预算为 128 KiB，包含最长合法 Unicode 名称和 ID 的边界验证。重名保留各自 `shopId`。`shopId = null` 的品牌范围不进入目录，也不能展开成全公司店铺。名称不授予 query 或其他业务动作。

服务端先用既有 `content_intake.authorization_deadline(principal, 'query', scope, source, at)` 得到可见店铺。只计入 `sources.mode = 'v2-preview'` 且 `scopes.shop_id IS NOT NULL` 的来源。任一来源的 query 期限非空，该店出现一次。legacy、v2-active、无 query 期限的店不出现。空集合返回空 `items`，这不是缺名称。可见集合里任一店没有当前名称时，整次 `409 SHOP_DISPLAY_MISSING`，不返回其余店。

只读失败追加在既有 `IntakeFailure.details.reason` 末尾，且只用于这个 GET：

| reason | HTTP | 含义 |
| --- | --- | --- |
| `SHOP_DIRECTORY_CURSOR` | 400 | cursor 或 limit 不符合合同，签名、limit 或页边界被篡改，或换了会话 |
| `SHOP_DIRECTORY_SESSION` | 401 | 主体不存在，或 ProductSession 未认证 |
| `SHOP_DISPLAY_MISSING` | 409 | 当前可见店缺少名称；调用方继续显示编号，不得用编号冒充名称 |
| `SHOP_DIRECTORY_CHANGED` | 409 | 事实版本、撤销代际、目录修订或可见集合摘要已变 |
| `SHOP_DIRECTORY_EXPIRED` | 409 | 主体事实不可用，或游标截止已到 |
| `SHOP_DIRECTORY_UNAVAILABLE` | 503 | 私有签名 key 尚未装配、已到期或被撤销 |

以上失败都不返回 `items`。CHANGED 与 EXPIRED 后必须丢弃已读页，从第一页重读。不得把旧页和新页拼成一份目录。

## 游标

`nextCursor` 为 `sd2.<factsVersion>.<revocationGeneration>.<directoryRevision>.<sha256>.<deadlineEpochUs>.<ordinal>.<limit>.<lastShopId>.<signature>`，总长不超过 512；不外发会话哈希。HMAC 签名绑定主体、tenant、app、会话及完整载荷。受信读取入口从私有当前 key 行派生 tenant/app/keyId/version 专属签名材料；即使操作者给新 keyId 重用了相同合成原始材料，旧游标仍拒绝。签名使用独立的服务端私有 `p_cursor_signing_key`（32 字节），不使用会话哈希或 bearer 派生值作 key；知道自己 token 的客户端仍不能重签。签名、页大小或会话不匹配均为 `SHOP_DIRECTORY_CURSOR`；修改序号和店铺两字段也不能跳页。

`sha256` 是按 `C` 排序的 `shopId:displayVersion` 用逗号连接后的摘要。`ordinal` 是完整有序集合中的 1 起序号。截止为事实有效期和所有可见店 query 期限的最小值，截断到毫秒；空集合用事实截止。受信入口再取会话和当前签名 key 截止的最小值。续页不得延长最初截止，即使期间授权续期；当前截止缩短则 `SHOP_DIRECTORY_CHANGED`。事实代际、目录修订或集合摘要变化要求整份重读。

内部存储接口为 `read_shop_directory(principal, session_hash, at, cursor, limit, cursor_signing_key, outer_deadline)`，末项可空仅为低层合成测试兼容。服务端填入身份、会话、校验时间及签名材料，不接受 HTTP 调用方传这些字段。存储函数在取得目录锁后按数据库当前时钟检查 enabled 身份事实，页面与 HMAC 完成、RETURN 前再次检查；等待和计算跨截止不能借用旧请求时间。可见集合物化为一个 jsonb 值，任一缺名称整单拒绝。

低层函数只绑定会话哈希，不能单独当会话验证器。新的 `prepare_shop_directory_read` / `prepare_shop_directory_write` / `manage_shop_directory_steward` 都先调用内部 `shop_directory_session_context`，直接核对真实 `backend_identity.sessions`、绑定、唯一 user→principal、当前事实和岗位。`principal.user_id` 的既有 UNIQUE 保证不会任意选取多个主体。

## 维护人生命周期与写入所有者

没有名称写 HTTP，也没有新 UI。选择继续沿用唯一外部事务所有者，加入窄的 prepare/finalize 函数；没有采用持有事务提交权的数据库 procedure，避免第二套提交语义和 PG15 SECURITY DEFINER procedure 无法控制事务的限制。

`shop_directory_registrars` 是显式 tenant/app 治理登记资格，由受控 bootstrap 所有者维护，运行角色无权自助获得。登记资格必须有版本、起止时间与撤销状态。登记操作人还必须在当前新鲜事实里唯一映射为 director 或 manager；岗位本身、单店 allocation 或品牌 query 都不自动生成 tenant 级资格。真实资格名单和 bootstrap 运维归属仍未获批。

`manage_shop_directory_steward(session_hash, target, expected_version, target_facts, valid_until, reason, operation)` 提供合成可运行的登记、撤销和轮换：首次 CAS 为 0，后续必须匹配当前版本；空 target 表示撤销。新维护人也须属于同一 tenant/app、身份未停用、事实新鲜且唯一映射为 director/manager。期限显式输入且不能晚于登记者资格截止，不自定业务保留期。每次成功追加不可变事件，记录操作人/事实版本、登记资格版本、前后维护人、目标事实版本、原因、操作 ID、请求摘要和结果，当前行版本加一。相同操作 ID 与相同内容重放原结果，不重做赋权；同 ID 异内容或旧 CAS 拒绝。提交结果未知时，同一操作 ID 可恢复原收据，历史收据不会恢复已经撤销的当前权限。

名称维护仍用 `upsert_shop_display(actor, tenant, app, shop, display_name, expected_revision)`，但仅受信 `prepare_shop_directory_write` 调用。写入人同时需要：当前唯一 director/manager、同 tenant/app 的显式有效 steward 登记、未停用身份、新鲜 enabled 事实。登记、名称写入、最终守卫均检查岗位；换岗为 agent/enabler 后立即拒绝。名称管理不插入 business grant，也不授予上传、发布或分配权限。

`expected_revision` 为空只允许尚无目录修订。以后必须匹配当前修订，否则 `SHOP_DIRECTORY_CONFLICT`；成功追加不可变名称历史并递增 displayVersion 与目录修订。名称写入的未知提交应重新读取修订和名称再决定，不能盲重试。GUC `directory_write` / `directory_steward_write` 只是一致性标记，客户端可 SET 自定义 GUC；实际边界是用途角色不能直接写表、执行低层函数或 SET ROLE 到属主。合成实库已用非 owner LOGIN 验证。

## 私有签名 key 生命周期

`shop_directory_keys` 只保留当前私有材料，轮换替换、撤销清空；`shop_directory_key_events` 只记版本/keyId/操作者/期限/原因/请求摘要/结果，不写原始 key。`rotate_shop_directory_key` 由独立基础设施用途角色执行，不从产品岗位或 steward 权限推导。入口使用 tenant/app CAS、操作 ID 重放、不可变审计、显式有限期限及写入后真实时钟检查；新 keyId 不可复用旧标识，派生签名材料绑定版本。旧游标在轮换后拒绝，到期或撤销时整个读取失败关闭。

当前只有一次性 PG 的固定合成 key。真实 secret、配置、持钥人和用途 ACL 均未创建。正式注入必须只从受控服务端 secret 通道到受限 key 操作入口，避免 SQL 参数被查询/错误日志采集；key 不可进入 renderer、HTTP 参数或返回值。实际持有、轮换周期、保管和日志配置仍须正式装配验证，不能以本地测试代替。

## 同一事务消费者

`sites/tests/support/shop-directory-consumer.mjs` 是可运行合成受信消费者。它只接受受控调用侧会话哈希和操作数据，拒绝额外 principal/tenant/app/key；不提供生产 HTTP 或认证适配。顺序为 BEGIN READ COMMITTED → `backend_review.lock_content()` → 会话/身份/事实行锁 → 目录操作 → `finish_shop_directory_transaction` → COMMIT，目录锁位于全局内容锁之后，与产品现有事务所有者一致。最终守卫重核当前会话、事实代际、岗位、登记版本、签名 key 及目录/query 结果，最后按数据库时钟检查最早截止。

唯一消费者负责最终守卫和提交：只有 COMMIT 确认成功后才输出业务值，提交前错误关闭事务，COMMIT 后断连或返回损坏保留 unknown；管理写入可用同操作 ID 恢复。私有 envelope 和会话引用不会外发。不声称数据库能阻止任意受信 SQL 调用者绕过 finalize 自行 COMMIT；正式产品必须复用既有 TS 事务 owner，而不是开放任意 SQL 或单独 prepare API。

新表包括 steward 当前行、registrar 资格、steward 事件、当前私有 key、key 事件、目录修订、名称历史和名称当前指针。新表/函数全部 REVOKE PUBLIC，既有应用角色没有新增 EXECUTE。本轮新 NOLOGIN 用途能力由 [安装 manifest](content-intake-runtime-candidate/installation.generated.json)明确登记，独立环境 LOGIN 通过唯一 membership 与 SET ROLE 消费。PG 夹具把 candidate 函数交给独立 NOLOGIN 非 superuser 属主，只给合成 LOGIN consumer 三种 prepare/manage 与 finalize 能力，另一 LOGIN 只持 key 轮换执行权；它们不能直读 key、越过低层接口或切换属主。用途 ACL 已随精确合同冻结；环境账号授权仍另行办理。

`sources` 不新增名称列；schema.v1.22 的 authorization_deadline、四岗业务上限、agent/enabler query 上限均保持冻结原字节。产品 authority.ts、0030 和 migration 编号未动。

## 产品最小接线

产品仓在批准、export、intake 和 codegen 之前不消费本候选。接线所有者是主 Agent，落点是 `loadIntakeAccess`：用同一个 ProductSession 把目录页读完，页集合的 `shopId` 必须与现有 `shops` 完全一致，只把 `IntakeQueryFilters` 里 option 的可见文案换成 `displayName`，option 的值仍是 `shopId`。任一页失败则整份菜单失败，继续显示编号。不新增 renderer preload channel。query 和 copy 仍传 `shopId`。品牌授权继续不能变成全公司店铺。建议补丁只在冻结 intake 之后修改 `content-intake-access.ts`、`IntakeQueryFilters.tsx`、合同锁和 codegen；本候选不修改这些文件。
