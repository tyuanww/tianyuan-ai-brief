## 边界

方案 A 把 `displayName` 放进每个 Source。同店的售前与商品来源会各自改名，分页时能拼出两个名字。方案 B 使用独立的 tenant/app/shop 目录，一个店铺只有一条当前名称和 `displayVersion`。本候选采用方案 B。`shopId` 继续拥有查询和复制身份；名称只替换菜单文案。

比较过的失败面：A 的写入面更小，但读结果会随来源漂移。B 多一张目录和一次修订，读路径却能用同一谓词给出一份完整集合。任务要求同店不同来源的名称和版本一致，因此取 B。

## 读合同

`GET /v1/intake/shop-directory`，`operationId` 为 `listIntakeShopDirectory`。认证只来自 `ProductSession`。调用方不能提交 principal、tenant、app、会话哈希或店铺名单。`limit` 为 1–100，缺省 50。响应 `Cache-Control: no-store`，正文是 `{items, nextCursor, validUntil}`。每条 item 只有 `shopId`、`displayName`、`displayVersion`。

`displayName` 去掉首尾空白后为 1–256 个字符，并且必须已经没有首尾空白。重名保留各自 `shopId`。`shopId = null` 的品牌范围不进入目录，也不能展开成全公司店铺。名称不授予 query 或其他业务动作。

服务端先用既有 `content_intake.authorization_deadline(principal, 'query', scope, source, at)` 得到可见店铺。只计入 `sources.mode = 'v2-preview'` 且 `scopes.shop_id IS NOT NULL` 的来源。任一来源的 query 期限非空，该店出现一次。legacy、v2-active、无 query 期限的店不出现。空集合返回空 `items`，这不是缺名称。可见集合里任一店没有当前名称时，整次 `409 SHOP_DISPLAY_MISSING`，不返回其余店。

只读失败追加在既有 `IntakeFailure.details.reason` 末尾，且只用于这个 GET：

| reason | HTTP | 含义 |
| --- | --- | --- |
| `SHOP_DIRECTORY_CURSOR` | 400 | cursor 或 limit 不符合合同，或页序号和店铺对不上 |
| `SHOP_DIRECTORY_SESSION` | 401 | 主体不存在，或续页会话哈希与本次产品会话不一致 |
| `SHOP_DISPLAY_MISSING` | 409 | 当前可见店缺少名称；调用方继续显示编号，不得用编号冒充名称 |
| `SHOP_DIRECTORY_CHANGED` | 409 | 事实版本、撤销代际、目录修订或可见集合摘要已变 |
| `SHOP_DIRECTORY_EXPIRED` | 409 | 主体事实不可用，或游标截止已到 |

以上失败都不返回 `items`。CHANGED 与 EXPIRED 后必须丢弃已读页，从第一页重读。不得把旧页和新页拼成一份目录。

## 游标

`nextCursor` 形如：

`sd1.<session64>.<factsVersion>.<revocationGeneration>.<directoryRevision>.<sha256>.<deadlineEpochUs>.<ordinal>.<lastShopId>`

总长不超过 512。`session64` 是服务端从当前 ProductSession 取得的会话哈希，不是请求参数。`sha256` 是按 `C` 排序的 `shopId:displayVersion` 用逗号连接后的 SHA-256；空集合是 `sha256('')`，不是 64 个 0。`deadlineEpochUs` 是本页 `validUntil` 的微秒整数。`ordinal` 是本页最后一条在完整有序集合中的 1 起序号。`validUntil` 是主体事实截止与各可见店 query 期限的最小值，截断到毫秒；空集合用事实截止。同一次目录的每一页使用同一个 `validUntil`。

续页按这个顺序失败：解析、会话哈希、事实版本和撤销代际、目录修订、截止、摘要、序号对应的店铺必须等于游标里的 shopId。因此同一修订内伪造上一页的最后一店，得到 `SHOP_DIRECTORY_CURSOR`，不会换一页数据。截止已到时即使集合也变了，仍返回 `SHOP_DIRECTORY_EXPIRED`。第一页 cursor 为空。

存储函数是 `content_intake.read_shop_directory(principal, session_hash, at, cursor, limit)`。这两个身份参数都由服务端填入。它把可见集合物化成一个 jsonb 值，避免连接池里的临时表计划在下一次调用时失效。

## 写入所有者

没有写 HTTP。名称只能由 `content_intake.upsert_shop_display(actor, tenant, app, shop, display_name, expected_revision)` 写入。

写入者必须是 `content_intake.shop_directory_stewards(tenant_id, app_id)` 里登记的主体，并且该主体属于同一 tenant/app。没有这行就失败关闭。登记行拒绝 UPDATE 和 DELETE。本候选不提供自助登记，不从岗位、飞书通讯录或品牌授权生成维护人。真实维护人尚未提供，测试只显式插入合成主体 `steward` / `steward-b`。

`expected_revision` 为空只允许在该 tenant/app 还没有目录修订时使用。之后必须等于当前修订，否则 `SHOP_DIRECTORY_CONFLICT`，并且不增加 `displayVersion`、不改当前指针。成功时追加历史行，`displayVersion` 从 1 递增，目录修订按 tenant/app 加 1。历史行拒绝 UPDATE 和 DELETE。当前指针和修订只有在事务局部 GUC `content_intake.directory_write=writing` 下才能写，调用方不能自己打开这个开关。同一 tenant/app 的写用事务级 advisory lock 串行。

写入失败留在 SQL，不进入 OpenAPI：`SHOP_DISPLAY_INVALID`、`SHOP_DIRECTORY_STEWARD_REQUIRED`、`SHOP_DIRECTORY_CONFLICT`、`SHOP_DISPLAY_IMMUTABLE`。upsert 不插入 grant。

## 和现有库的差异

新表只有 `shop_directory_stewards`、`shop_directory_revisions`、`shop_displays`、`shop_display_current`。`sources` 不增加名称列。授权谓词仍是 schema.v1.22 里的 `authorization_deadline`，包括四岗业务上限和 agent/enabler 新操作只 query 的 HAVING。本候选不修改该函数，不修改产品 `authority.ts`，也不占用产品 overlay `0030` 或后续 migration 编号。四个新函数和四张新表都 `REVOKE ALL FROM PUBLIC`。

## 产品最小接线

产品仓在批准、export、intake 和 codegen 之前不消费本候选。接线所有者是主 Agent，落点是 `loadIntakeAccess`：用同一个 ProductSession 把目录页读完，页集合的 `shopId` 必须与现有 `shops` 完全一致，只把 `IntakeQueryFilters` 里 option 的可见文案换成 `displayName`，option 的值仍是 `shopId`。任一页失败则整份菜单失败，继续显示编号。不新增 renderer preload channel。query 和 copy 仍传 `shopId`。品牌授权继续不能变成全公司店铺。建议补丁只在冻结 intake 之后修改 `content-intake-access.ts`、`IntakeQueryFilters.tsx`、合同锁和 codegen；本候选不修改这些文件。

## 尚缺的业务决定

- 真实目录维护人是谁，以及不可变登记行将来如何轮换。本候选没有轮换操作。
- 每个真实店铺的正式名称由谁确认。这里的名称全部是合成 fixture，不能当成飞书已经提供了业务店铺名。
- A/B 回收后 1.21.0 / schema.v1.23 是否仍是批准版本号。
